# MQB CAN protocol reference

Bus: **Komfort- / Infotainment-CAN, 500 kbit/s**, standard 11-bit identifiers.

Signal layouts follow `vw_mqb_2010.dbc` (commaai/opendbc). All signals are
little-endian (Intel, `@1+` in DBC notation): bit *n* means bit `n & 7` of byte
`n >> 3`, and multi-bit signals extend upward from their start bit,
least-significant bit first.

## Terminals (Klemmen)

German automotive terminal designations, per DIN 72552:

| Terminal | Meaning | Emulated here? |
|---|---|---|
| **Kl. 30** | Permanent battery positive, always live | **No — physical only.** No CAN representation exists. Supply it from a PSU. |
| **Kl. 31** | Ground | No — physical only |
| **Kl. S** | Key inserted in barrel | Yes |
| **Kl. 15** | Ignition on ("run") | Yes — the point of this project |
| **Kl. X** | Load shedding; drops during cranking so the starter gets the current | Yes |
| **Kl. 50** | Starter request (momentary, while cranking) | Yes |

On MQB the physical T15 rail is generated by the body control module, but
modules act on the CAN broadcast. That is why emulating the message works
without a BCM present.

Terminals normally progress `30` → `30+S` → `30+S+15` → `30+S+15+50` (crank,
with X dropping) → back to `30+S+15`.

## `Klemmen_Status_01` — ID `0x3C0` (960)

DLC 4, cycle **100 ms**, sender Gateway/BCM.

```
        byte 0        byte 1        byte 2        byte 3
     ┌───────────┬───────────┬─────────────────┬───────────┐
     │ CHECKSUM  │ COUNTER   │ terminal flags  │  reserved │
     │  (8 bit)  │ (4 bit)   │                 │   0x00    │
     └───────────┴───────────┴─────────────────┴───────────┘
```

| Signal | Start bit | Len | Location |
|---|---|---|---|
| `CHECKSUM` | 0 | 8 | byte 0 |
| `COUNTER` | 8 | 4 | byte 1, low nibble |
| `ZAS_Kl_S` | 16 | 1 | byte 2, bit 0 |
| `ZAS_Kl_15` | 17 | 1 | byte 2, bit 1 |
| `ZAS_Kl_X` | 18 | 1 | byte 2, bit 2 |
| `ZAS_Kl_50` | 19 | 1 | byte 2, bit 3 |

Byte 1's high nibble, byte 2's bits 4–7 and byte 3 are unused and sent as zero.

### Byte 2 values

| Value | State |
|---|---|
| `0x00` | Everything off — Kl. 30 only |
| `0x01` | Key inserted |
| `0x03` | **Ignition on** (S + 15) — the usual target |
| `0x07` | Ignition on with load shedding |
| `0x0B` | Cranking (S + 15 + 50) |

### Counter

Byte 1 increments `0x0 … 0xF` then wraps, **once per transmitted frame**.
Receivers treat a gap in the sequence as a fault, so it must only advance on a
frame that actually went out on the wire — not on one the controller rejected.

### Checksum

Byte 0 is an AUTOSAR E2E-style CRC:

| Parameter | Value |
|---|---|
| Width | 8 bits |
| Polynomial | `0x2F` |
| Initial value | `0xFF` |
| Reflect in / out | no / no |
| Final XOR | `0xFF` |
| Input | bytes 1, 2, 3, then the magic byte |
| Magic byte for `0x3C0` | **`0xC3`** |

The magic byte is per-message-ID; other MQB messages use different ones.

```c
uint8_t crc = 0xFF;
for (each of bytes 1..3, then 0xC3) {
    crc ^= byte;
    for (8 iterations)
        crc = (crc & 0x80) ? (crc << 1) ^ 0x2F : (crc << 1);
}
checksum = crc ^ 0xFF;
```

### How the magic byte was determined

Published bench setups hardcode this 16-entry table — the checksums for
`byte2 == 0x03` at each counter value:

```
0x74 0xC1 0x31 0x84 0xFE 0x4B 0xBB 0x0E
0x4F 0xFA 0x0A 0xBF 0xC5 0x70 0x80 0x35
```

Assuming CRC-8/AUTOSAR and brute-forcing the magic byte against all 16 entries
yields exactly one candidate, `0xC3`, consistent across every counter value —
which is strong evidence the algorithm is right rather than a coincidental fit:

```python
def crc8_2f(data, init=0xFF):
    c = init
    for b in data:
        c ^= b
        for _ in range(8):
            c = ((c << 1) ^ 0x2F) & 0xFF if (c & 0x80) else (c << 1) & 0xFF
    return c

forum = [0x74,0xC1,0x31,0x84,0xFE,0x4B,0xBB,0x0E,
         0x4F,0xFA,0x0A,0xBF,0xC5,0x70,0x80,0x35]

for ctr in range(16):
    magic = [m for m in range(256)
             if crc8_2f([ctr, 0x03, 0x00, m]) ^ 0xFF == forum[ctr]]
    print(ctr, [hex(m) for m in magic])   # -> ['0xc3'] for every counter
```

This matters practically. A hardcoded table only covers `byte2 == 0x03`, so it
can only ever say "ignition on". Computing the CRC means valid frames for
ignition **off**, for Klemme X and for cranking — none of which the table can
produce. `mqbChecksumSelfTest()` pins the implementation to all 16 reference
values and runs both in `test/run.sh` and on the Arduino at boot.

The same answer exists independently: commaai/opendbc's VW checksum
(`opendbc/car/volkswagen/mqbcan.py`, `VOLKSWAGEN_MQB_MEB_CONSTANTS`) lists
`0x3C0: [0xC3] * 16`, and its test suite
(`opendbc/can/tests/test_checksums.py`,
`test_volkswagen_mqb_crc_klemmen_status_01`) checks the very same 16 frames.

### Example frames

| State | byte 2 | Counter 0 | 1 | 2 | 3 |
|---|---|---|---|---|---|
| Ignition off | `0x00` | `66 00 00 00` | `D3 01 00 00` | `23 02 00 00` | `96 03 00 00` |
| Ignition on | `0x03` | `74 00 03 00` | `C1 01 03 00` | `31 02 03 00` | `84 03 03 00` |
| Cranking | `0x0B` | `04 00 0B 00` | `B1 01 0B 00` | `41 02 0B 00` | `F4 03 0B 00` |

## `Dimmung_01` — ID `0x5F0` (1520)

DLC 8, cycle ~500 ms (assumed — see note below). Display and panel dimming.
**No checksum, no counter.**

| Signal | Start bit | Len | Location | Range |
|---|---|---|---|---|
| `DI_KL_58xd` | 0 | 8 | byte 0 | 0–253 |
| `DI_KL_58xs` | 8 | 7 | byte 1, bits 0–6 | 0–100 % |
| `DI_Display_Nachtdesign` | 15 | 1 | byte 1, bit 7 | 0–1 |
| `DI_KL_58xt` | 16 | 7 | byte 2, bits 0–6 | 0–100 % |
| `DI_Fotosensor` | 24 | 16 | bytes 3–4 (LSB first) | 0–65535 |

Bytes 5–7 are unused, sent as zero.

Example — `58xd=200`, `58xs=77`, night design on, `58xt=61`, sensor `0xBEEF`:

```
C8 CD 3D EF BE 00 00 00
```

## `Diagnose_01` — ID `0x6B2` (1714)

DLC 8, cycle ~1000 ms (assumed). Odometer plus the date and time — this is
where a MIB head unit gets its clock. **No checksum, no counter.**

The `UH_*` ("Uhrzeit") signals are what matter for the clock; the DBC groups
them into this message rather than a separate `Uhrzeit_01`.

| Signal | Start bit | Len | Location | Range |
|---|---|---|---|---|
| `DGN_Verlernzaehler` | 0 | 8 | byte 0 | 0–254 |
| `KBI_Kilometerstand` | 8 | 20 | byte 1, byte 2, byte 3 bits 0–3 | 0–1048573 km |
| `UH_Jahr` | 28 | 7 | byte 3 bits 4–7, byte 4 bits 0–2 | **+2000 offset** |
| `UH_Monat` | 35 | 4 | byte 4, bits 3–6 | 1–12 |
| `UH_Tag` | 39 | 5 | byte 4 bit 7, byte 5 bits 0–3 | 1–31 |
| `UH_Stunde` | 44 | 5 | byte 5 bits 4–7, byte 6 bit 0 | 0–23 |
| `UH_Minute` | 49 | 6 | byte 6, bits 1–6 | 0–59 |
| `UH_Sekunde` | 55 | 6 | byte 6 bit 7, byte 7 bits 0–4 | 0–59 |
| `Kombi_02_alt` | 62 | 1 | byte 7, bit 6 | 0–1 |
| `Uhrzeit_01_alt` | 63 | 1 | byte 7, bit 7 | 0–1 |

Note `UH_Jahr` carries an offset of 2000: the year 2026 is encoded as 26. Most
of these signals straddle byte boundaries, which is why `mqb_mib.cpp` uses a
generic bit packer (`packLE`) rather than hand-written shifts.

Example — 2026-08-22 16:45:33, odometer 123456 km:

```
00 40 E2 A1 41 0B DB 10
```

## `VIN_01` — ID `0x6B4` (1716)

DLC 8, cycle 200 ms per frame (assumed). The vehicle identification number,
spread over three frames that are told apart by a multiplexer in the low two
bits of byte 0. **No checksum, no counter.**

| Byte 0 | Bytes 1–4 | Bytes 5–7 |
|---|---|---|
| `00` | `KS_Geheimnis_1`…`4` | VIN characters 1–3 |
| `01` | VIN characters 4–7 | VIN characters 8–10 |
| `02` | VIN characters 11–14 | VIN characters 15–17 |

The characters are plain ASCII, one per byte.

**On a car the gateway sends this message.** It holds the VIN itself and
repeats it for the other control units; the DBC names `Gateway_MQB` as the
sender. So there is no broadcast that tells a gateway its VIN: a gateway is
given its VIN by a tester, as a diagnostic write. What the emulator can do is
stand in for a gateway towards the units on its own bus.

`KS_Geheimnis` is the component-protection secret, known to a real gateway and
its car and not to this project. The emulator sends those four bytes as zero,
so a unit that checks them will not be satisfied by this message.

Off by default. `V` and the 17 characters on the console start it, `V-` stops
it, and a reset forgets it. Sent whatever the ignition, and withheld while
another node sends the ID.

Example — `BENCH0123456789AZ`:

```
00 00 00 00 00 42 45 4E
01 43 48 30 31 32 33 34
02 35 36 37 38 39 41 5A
```

## Cycle times

The opendbc DBC carries no `GenMsgCycleTime` attributes, so:

- `0x3C0` at **100 ms** is well established and corroborated by bench reports.
- `0x6B2` at **1000 ms** is measured: a J533 gateway on the bench sends it at
  that rate (999–1001 ms).
- `0x5F0` at 500 ms is a **plausible default, not a measured value.** The
  gateway alone does not send it.
- `0x6B4` at 200 ms per frame is **assumed, not measured.** The gateway on the
  bench does not send it on the convenience bus.

Use the firmware's sniffer (`p`) against a real car to confirm, and adjust
`DIMMUNG_CYCLE_MS` / `DIAGNOSE_CYCLE_MS` / `VIN_CYCLE_MS` in `config.h`. Cycle accuracy matters:
some receivers flag a sender as faulty if a cyclic message drifts more than
roughly ±10 % from its nominal period.

## Supply voltage: no documented broadcast

The emulator shows the supply voltage from one byte of a CAN frame, and which
frame that should be on MQB is not publicly documented. What a search of the
public sources turned up:

- **opendbc** (`vw_mqb.dbc`, `vw_mqbevo.dbc`, `vw_mlb.dbc`): no 12 V battery
  or terminal 30 voltage signal. The voltage signals there belong to the
  hybrid DC/DC converter and the high-voltage battery.
- **PQ platform** (`vw_pq.dbc`): `BSG_Last`, ID `0x570`, carries
  `Batteriespannung_Bordnetzbatter`, 8 bits from bit 16, 0.05 V per bit plus
  5 V. That is the older platform; an MQB gateway on the bench did not send
  `0x570`.
- **The standard way** is not a broadcast but a question: OBD-II service
  `01`, PID `42`, "control module voltage", asked on `0x7DF` and answered by
  the engine control unit on `0x7E8`. It needs an engine control unit on the
  bus, and it makes the emulator a second tester, which this project avoids
  next to a tester that may be flashing.
- **Volkswagen's own way** is a UDS measured value read from a control unit
  with service `22`. ODIS shows the identifier of each measured value in its
  RDID column: in the gateway on the bench, *Battery voltage* is `$2A07`
  (12.720 V when it was read), next to *Specified generator voltage* `$2A00`
  and *Battery voltage at rest* `$2A10`, which both read 15.0 V there.

That measured value is what the broadcast was compared against. The gateway's
`0x663`, every 100 ms, held `78 28 20 0E 1F 9A 2C 00` and
`78 28 20 0E 1F 9B 2C 00` in turn: byte 5 flickering between 154 and 155. With
the PQ scaling above, 0.05 V per bit plus 5 V, those are 12.70 and 12.75 V,
one step either side of the 12.720 V the gateway reported. Hence the default
in `config.h`: byte 5 of `0x663`, 50 mV per bit, 5000 mV offset. It is one
point on a line, so it stays marked unverified until the value has been seen
to follow the supply. Byte 0, the earlier guess at 0.1 V per bit, is a
constant `0x78`.

## Adding another message

1. Add the ID, DLC and a `…State` struct to `mqb_mib.h`, or a file pair of
   its own as `mqb_vin.{h,cpp}` is.
2. Write a `buildX()` in `mqb_mib.cpp` using `packLE()` — zero the buffer first,
   then pack each signal.
3. If it has a checksum, reuse `mqbChecksum()` with that message's magic byte;
   derive the magic byte the same way as above from captured frames.
4. Add a round-trip test in `test/test_klemmen.cpp`, including a maxed-fields
   case to catch signals bleeding into neighbours.
5. Schedule it in `loop()` with `due()`.

Keep builders in the `mqb_*` files, free of Arduino dependencies, so they stay
host-testable.
